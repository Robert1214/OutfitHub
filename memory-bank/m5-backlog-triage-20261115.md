## 2. 回答杂音

用户此前反馈「回答有杂音」。本次跑 3 题（R01 单品、R02 澄清、H02 搭配）逐句看，找到 2 类可定位的表达问题：

| 编号 | 现象 | 原文 | 判断 |
| --- | --- | --- | --- |
| N-01 | 把内部核对条件原样列出 | R01：「本次核对的是“极简风、下装、单件预算、不含鞋、当前在售”，这些条件都匹配。」 | `checkedConstraints` 是工具字段，规则 §12.12 第 3 条已明确「不逐条转述」，模型仍转述了 |
| N-02 | 对顾客解释「这是单件不是整套」 | R01：「这是单件选购，不是整套搭配。」 | 规则里是防止模型把单品说成整套的内部约束；对顾客说这句没有信息量，属内部口径外泄 |

另有一处**非杂音但值得注意**：

- R02 问品类时用了「**裙装**」一词（「裤子，还是裙装？」）。这是正常的中文泛指，不是品类误称，但 PM-011 的教训是「裙/裤」容易混，题库里需要专门有一道「顾客说裤子，回答不能出现裙」的检查项。

**未发现**的杂音：没有内部 ID、规则编号、字段名、样例编号、镜像思考内容。

### 建议

- 这两条都可以**只改回答节点规则**（在表达段加一句「不列已核对条件清单；不向顾客解释内部范围限定」），不改代码。
- 因为属于文案问题，建议**先纳入题库**，跑出稳定复现再改，避免又一次「改坏了不知情」。

## 3. 会话过期（PM-014）

### 代码核对

`src/app/api/chat/route.ts` 约 420 行：

```
...(event.status === 404 || /Conversation Not Exists/i.test(streamError)
  ? { code: "conversation_expired" } : {}),
```

前端收到 `conversation_expired` 后丢弃旧 conversationId 重新开始。**逻辑存在。**

### 实测状态

- 未构造「过期 conversationId」的真实请求。Dify 的会话不存在时会返回 404 或 `Conversation Not Exists`，但本地 Dify 删除会话成本较高，本轮未做。
- 与 D1 那次事故的区别：D1 是**每个请求换了 Dify user**，导致旧 conversationId 归属新 user 而 404。该根因已修（anonId 固定），本次无需重查。

### 建议

放进题库：用「伪造一个不存在的 conversationId」发请求，看是否返回 `conversation_expired` 且前端能恢复。这条可以纯脚本测，不需要真的删会话。
