## 4. H03定位：不是算错359，也不是没库存

顾客原话：

> 这件衬衫我衣柜里有了，只给它配条极简裤子。裤子单件三百五十九封顶，别加鞋。

同轮提取、代码输入输出和HTTP均包含：

```json
{
  "intent": "outfit",
  "category": "bottoms",
  "budgetCents": 35900,
  "budgetScope": "item",
  "includeCurrentProduct": false,
  "anchorProductId": "cmvy255tt000caotqizp21rtq",
  "otherRequirements": ["已有衬衫，无需购买上装", "不要鞋"]
}
```

`includeCurrentProduct=false`已经表达预算不含上衣。模型又在otherRequirements重复表达这件事。工具为避免悄悄忽略真实附加要求，会把未识别条目列入unresolvedRequirements；本轮正是该重复条目触发needs_verification、空products。回答随后遵循了这个错误阻断，但“再按只买下装重查”没有新增信息，未解决顾客任务。

受控验证不调用模型、也不改数据库：

| 工具输入 | 唯一差别 | 实际结果 |
| --- | --- | --- |
| 原样回放失败requirements | 无 | needs_verification，未核实项为已有衬衫/无需购买上装 |
| 保留全部其他字段 | 只从otherRequirements删除这条重复描述 | matched_known_constraints，359元裤子，assessedPriceCents=35900，余额0 |

因此可以确认阻断来源是重复的语义表示与保守工具契约相遇；没有证据说明基模不会理解中文数字、数据库缺货或审美规则不足。原Prompt已有避免重复的原则但没有稳定遵守，不能声称“只是缺一句话”或已证明哪种改法最优。

首个修复假设：在提取第8条紧邻预算包含关系处明确“已拥有主体只更新专用字段”，补一个通用例子，同时要求保留防水等真正额外条件。先单独检验Prompt遵循是否改善；不删除未知条件保护、不直接把所有needs_verification改成成功、不换模型或顺便调整温度。
