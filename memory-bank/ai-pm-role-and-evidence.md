# AI 产品经理角色与项目能力证明标准

> 版本：v0.2（2026-11-04）
> 状态：待你确认和修改；确认后作为本项目的长期协作标准。
> 目的：明确哪些是 AI PM 本人必须做的、哪些是 AI 辅助完成的，以及这个项目如何在求职中证明能力。

---

## 1. 一句话原则

> **你负责问题、判断、取舍、验收和叙事；AI 负责在你批准的范围内外执行、分析和起草。**

AI 可以写代码、改 Prompt、跑评测、分析日志、起草文档，但不能替你决定：

- 做什么、不做什么
- 什么算对
- 哪个问题优先
- 哪些风险必须守
- 最终对用户承诺什么

如果面试时你只能解释“AI 帮我做的”，不能解释“我为什么这样决定”，那部分还不算你的能力证明。

## 2. 角色分工

### 2.1 你（AI 产品经理）必须负责

| 职责 | 具体产出 |
| --- | --- |
| 问题定义 | 用户是谁、痛点是什么、为什么需要导购助手 |
| 范围管理 | v1 做什么、不做什么；只读工具、演示支付、M5 优先 |
| 产品规则 | 退换按商品、肤色规则、无性别风澄清、售罄处理 |
| 优先级 | 先修哪个失败、哪些已知限制可以接受 |
| 验收标准 | 什么回答算对、商品命中几件算通过、什么情况转人工 |
| 取舍 | LLM vs 规则、Dify vs Next、RAG vs 工具、成本 vs 体验 |
| 数据定义 | 商品字段、标签、场景、可退/不可退、尺码数据 |
| 风险与合规 | 不编造、不歧视、不承诺显白/正品/发货、演示标识 |
| 用户沟通 | 追问、澄清、转人工、错误文案 |
| 复盘与叙事 | 失败分类、迭代记录、面试讲述、项目边界 |

### 2.2 AI 辅助完成

| 工作 | AI 可以做什么 | 你必须做什么 |
| --- | --- | --- |
| 调研 | 整理方案、对比优缺点 | 选择最终方向 |
| 架构 | 给出 Dify/Next/工具/RAG 方案 | 拍板取舍 |
| 编码 | 写 Route Handler、组件、脚本 | 确认范围和验收 |
| Prompt | 起草 Prompt、规则、示例 | 确认产品行为和话术 |
| 评测 | 建 CSV、跑脚本、算指标 | 定义期望行为和通过标准 |
| 失败分析 | 查日志、定位原因、给候选修复 | 判断是否值得修、怎么修 |
| 文档 | 起草 PRD、契约、复盘 | 审核、修改、用自己的话复述 |
| 测试 | 跑单条/全量评测 | 验收结果、决定是否接受 |

### 2.3 AI 不应替你决定

- 产品范围变更
- 新功能优先级
- 用户可见规则和承诺
- 评测期望和通过阈值
- 敏感话题（肤色、性别、医疗、正品）的处理方式
- 是否接受某个已知缺陷
- 最终项目叙事和面试表达

遇到这些，AI 应该停下来问，而不是“先做了再说”。

## 3. 每个迭代的协作协议

### 第一步：你定义

每个需求开始前，你先给出：

- 用户问题
- 期望行为
- 不做什么
- 验收标准
- 优先级

### 第二步：AI 给选项

AI 只提供：

- 事实
- 可选方案
- 每个方案的影响
- 风险和成本

AI 不替你做产品选择。

### 第三步：你拍板

你明确选择方案后，AI 才能在批准范围内改代码、Prompt、评测或文档。

### 第四步：AI 执行并报告

AI 报告：

- 改了什么
- 测试结果
- 哪些通过、哪些失败
- 哪些是上游波动、哪些是真实缺口

### 第五步：你验收并记录

你用自己的话写 3–5 条决策记录，例如：

```text
我决定 G05 黑黄皮按肤色较暗处理，先转人工，不直接推荐。
原因：肤色判断容易误判，先降低错误推荐风险。
代价：部分用户会觉得没有直接得到推荐。
```

没有这一步，项目容易变成“AI 做的”，而不是“你的作品”。

## 4. 这个项目如何证明 AI PM 能力

### 4.1 问题定义与范围

能讲清楚：

- 为什么做服装店导购，而不是泛聊天机器人
- 为什么只做到“收钱前一步”
- 为什么 M5 导购优先于 M4 试穿
- 为什么 v1 工具只读

**证明能力：** 能收敛范围，不被“什么都能做”带跑。

### 4.2 AI 架构判断

能讲清楚：

- 商品事实走数据库工具，不走知识库
- 尺码用 `size-engine`，不让 LLM 猜
- 商品上下文走 Start 变量，不拼进用户问题
- Dify 负责路由/语言，Next 负责权限/事实/输出契约

**证明能力：** 知道 LLM 适合什么、不适合什么。

### 4.3 评测与迭代

能讲清楚：

- 49 条评测集怎么来的
- gold cases、行为检查、商品命中、无效 ID、延迟
- 失败分类：意图、槽位、上下文、检索、格式、幻觉
- baseline 从 16.7% 到 90%+ 的迭代过程
- 哪些失败是上游波动，哪些是真实缺口

**证明能力：** 用数据驱动迭代，而不是凭感觉改 Prompt。

### 4.4 取舍与风险

能讲清楚：

- 为什么肤色问题先问冷暖
- 为什么“黑黄皮”按较暗处理、转人工
- 为什么无性别风需要先澄清
- 为什么避雷色不出商品卡片
- 为什么售罄商品要明示，并给替代款

**证明能力：** 能处理模糊、敏感和高风险场景。

### 4.5 可观测与护栏

能讲清楚：

- 无效商品 ID 校验
- 权限和 session
- 错误文案与上游日志分离
- 演示环境标识
- 不编造商品、价格、库存、折扣

**证明能力：** 知道 AI 产品上线前必须有哪些护栏。

## 5. 哪些不算能力证明

以下内容只能说明“你参与了实现”，不能单独证明 AI PM 能力：

- 写了多少行代码
- 改了多少次 Prompt
- 跑了多少次评测
- 文档字数
- UI 做得漂亮
- 复制 AI 生成的方案

面试官更关心：

- 你为什么这样定义问题
- 你为什么选这个方案
- 你怎么知道它有效
- 失败时你怎么定位和取舍
- 哪些风险你提前挡住了

## 7. 面试讲述模板

### 3 分钟版本

```text
1. 问题：服装店商品少、决策重，用户需要导购帮助找商品、看搭配、问政策。
2. 范围：只做到支付前，工具只读，不接真实支付/物流。
3. 架构：Dify 负责意图路由和语言，Next 负责权限、商品事实、尺码和输出校验。
4. 评测：49 条评测集，覆盖商品、政策、尺码、肤色、售罄、注入。
5. 迭代：从 16.7% 商品命中开始，定位上下文、检索、参数提取问题，做到 90%+。
6. 取舍：尺码不让 LLM 猜；肤色先问冷暖；售罄不推荐；高风险转人工。
```

### 10 分钟版本

在 3 分钟版本上补充：

- 一个失败案例的定位过程
- 一个产品规则的形成过程
- 一个取舍的代价
- 一个已知限制和下一步

## 8. Ownership 自检四问（下一步开始前必问）

从这一版开始，**每次进入下一步之前，AI 必须先问你这四个问题**，不能直接开始改代码、Prompt 或评测。

### 四个问题

1. **没有 AI，你能重新设计这套评测吗？**  
   你能不能自己说出：评测维度、关键 case、什么算通过、为什么要这些 case。

2. **你能解释每个 Dify 节点为什么存在吗？**  
   你能不能说出：Start、分类器、参数提取、HTTP 工具、回答 LLM、Answer 各自解决什么问题，为什么不是别的结构。

3. **回答错了，你能定位是哪一层的问题吗？**  
   你能不能区分：意图错、上下文没传、参数提取错、检索错、回答生成错、格式/输出契约错。

4. **你能不看文档讲 10 分钟，并解释取舍吗？**  
   你能不能讲清楚：为什么这样做、代价是什么、哪些是已知限制、下一步怎么验证。

### 使用规则

- AI 问完之前，不开始下一步。
- 你不必一次全答对；**答不上来的部分，就是这一步要补的 ownership**。
- AI 可以补充事实、例子和选项，但**不能替你回答这四个问题**。
- 你的回答要能用自己的话讲出来，不能只复述 AI 的总结。
- 四个问题都过不了时，优先做“补 ownership”，而不是继续堆功能。

### 下一步开始前的固定问法

```text
在开始这一步之前，先做 ownership 自检：

1. 没有 AI，你能重新设计这套评测吗？
2. 你能解释每个 Dify 节点为什么存在吗？
3. 回答错了，你能定位是哪一层的问题吗？
4. 你能不看文档讲 10 分钟，并解释取舍吗？

你可以先答能答的部分；答不上来的，我补事实和选项，但产品判断仍由你做。
```

## 9. 每次迭代的检查清单

开始前：

- [ ] 先回答 Ownership 自检四问
- [ ] 用户问题是什么？
- [ ] 期望行为是什么？
- [ ] 不做什么？
- [ ] 验收标准是什么？
- [ ] 优先级是什么？

执行中：

- [ ] AI 是否只给了选项，没有替我做产品决定？
- [ ] 是否在批准范围内？
- [ ] 是否记录了决策和代价？

结束后：

- [ ] 测试结果是什么？
- [ ] 哪些通过、哪些失败？
- [ ] 失败是真实缺口还是上游波动？
- [ ] 我能不能用自己的话解释为什么这样做？
- [ ] 是否更新了评测和文档？
