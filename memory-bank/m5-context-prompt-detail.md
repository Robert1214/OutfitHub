## 1. 这一步解决什么问题

用户从商品详情页点「问导购」后，会说：

- 「这件是什么材质？」
- 「这个码我穿会紧吗？」
- 「这件可以退吗？」
- 「我看中了这件，有什么搭配推荐？」

这里的「这件 / 这个码 / 它」是**指代**。Dify 本身不知道用户从哪个商品页进来，如果只把用户原话发给它，模型只能猜。

商品上下文要解决三件事：

1. **指代消解**：让模型知道「这件」对应哪个商品。
2. **信息源优先级**：当前商品资料和商品工具结果冲突时，谁说了算。
3. **失败边界**：没有上下文、没有搜索结果、不能编造时，应该怎么回答。

这不是单纯的「提示词措辞」问题，而是**上下文工程**问题。

## 2. 数据流

```text
商品详情页
  └─ 点击「问导购」
      → /assistant?product=<product-slug>
      → 页面显示「正在咨询：<商品名>」
      → 前端 POST /api/chat
          {
            query,
            conversationId,
            anonId,
            productSlug
          }
      → Next 用 Prisma 查商品
      → 调 Dify /chat-messages，inputs 中带：
          {
            product_id,
            product_name,
            product_slug,
            product_context
          }
      → Dify Start 节点的 product_context
      → 回答 LLM
      → Answer
```

关键点：

- **用户问题**仍然只包含用户原话。
- **商品上下文**走 Dify 的 Start 输入变量，不拼进用户问题。
- `product_context` 是 JSON 字符串，包含当前商品的完整快照。

当前 `product_context` 包含：

```text
id、name、slug、description、priceCents、color、sizeLabel、refType、
material、careInstructions、tags、styleTags、occasionTags、
returnPolicy、fitType、chestCm、lengthCm、waistCm、hipCm、
pantsLengthCm、status、category{name, slug}
```

其中：

- `returnPolicy`：`RETURNABLE` = 支持退换（演示），`NO_RETURN` = 不支持退换（演示）。
- `status`：用于判断是否已售出。
- 尺码数据：用于回答当前商品的成衣尺寸；真正的合身判断仍由 `size-engine` 负责，不交给 LLM 猜。

## 3. Dify 侧最小配置

### 3.1 Start 节点

打开 Chatflow → Start 节点 → 右侧「输入字段」→ 点 `+`：

| 配置项 | 值 |
| --- | --- |
| 变量名称 | `product_context` |
| 显示名称 | `当前商品资料` |
| 字段类型 | **段落** |
| 最大长度 | `4000`（如果有这一项） |
| 必填 | 关闭（可选） |

**不要选「文本」**：Dify 的文本输入上限是 256 字符，商品 JSON 会超；段落类型没有这个限制。

这是一次性配置，不需要每次聊天手动输入商品。Next 每次请求会自动传入。

### 3.2 回答 LLM

原来的开头如果是：

```text
只根据下面的商品工具结果回答。
```

改成：

```text
请根据“当前商品资料”和下面的商品工具结果回答。
```

然后在 Prompt 最前面加入：

```text
当前商品资料（用户问“这件/这款/它”时优先使用；为空则忽略）：
{{#start.product_context#}}
```

`{{#start.product_context#}}` 不要手打：在 Prompt 输入框输入 `{`，选择 Start → `product_context`。  
手打容易因为变量重命名或路径不一致而失效。

### 3.3 发布后检查

调用 Dify 的 `/v1/parameters`，确认 `user_input_form` 中出现：

```json
{
  "variable": "product_context",
  "label": "当前商品资料",
  "type": "paragraph",
  "required": false
}
```

如果没有，说明 Start 节点没加成功，Dify 会直接忽略 `product_context`，回答仍会拿错商品。

## 4. 为什么 Prompt 要这样写

### 4.1 当前商品资料 = 指代消解

Dify 不读商品详情页。`product_context` 是系统告诉模型的「用户正在看哪件商品」。

没有它：

- 用户说「这件是什么材质」→ 模型不知道「这件」是谁。
- 商品工具按关键词搜索 → 可能返回黑色真丝衬衫。
- 模型按「只根据工具结果」回答 → 就会把黑色衬衫说成当前商品。

这正是实际发生过的错误：从米白针织开衫进入，问材质，回答成了黑色真丝衬衫。

### 4.2 为什么不能把商品资料拼进用户问题

看起来最简单的方法是：

```text
当前商品：米白针织开衫（ID: xxx）。用户问题：这件是什么材质？
```

但这样会污染整条链路：

- **意图分类器**会把商品名当成用户意图的一部分。
- **参数提取 LLM** 可能把商品名提取成 `q`。
- **商品工具**只按 `q=米白针织开衫` 搜索，结果只返回当前商品。
- 问「相似款 / 搭配」时，推荐链路就坏了。

实际测试过：把商品名拼进 query 后，问「有没有和这件相似的款」，工具只返回当前商品本身，无法推荐其他商品。

所以要把两类信息分开：

| 信息 | 走什么通道 |
| --- | --- |
| 用户说了什么 | `query` |
| 系统知道什么（当前商品） | Start 输入变量 `product_context` |
| 商品目录检索结果 | 商品工具结果 |

这就是「用户问题」和「系统上下文」的职责分离。

### 4.3 为什么开头要改「只根据工具结果」

商品工具的输出字段是为**搜索和商品卡片**设计的，只包含：

```text
id、slug、name、priceCents、color、sizeLabel、refType、
categoryName、categorySlug、tags、styleTags、occasionTags、
returnPolicy、imageUrl
```

它**不包含**：

- 材质
- 商品描述
- 护理说明
- 成衣胸围/衣长/腰围/臀围/裤长

用户问「这件是什么材质」，如果提示词仍写着「只根据商品工具结果回答」，模型只有两个选择：

1. 拿工具结果里另一个商品的数据 → 答错商品。
2. 自己编一个材质 → 幻觉。

所以必须把信息源范围改成「当前商品资料 + 商品工具结果」，并且规定：

- 问当前商品本身 → 用当前商品资料。
- 问搭配/推荐 → 用商品工具结果。

### 4.4 为什么分「当前商品本身」和「搭配/推荐」

这是两种不同任务：

| 用户意图 | 任务类型 | 主要信息源 |
| --- | --- | --- |
| 这件是什么材质/价格/颜色/退换 | 商品实体问答 | `product_context` |
| 这件怎么搭配、有没有相似款 | 商品目录检索 | 商品工具结果 |

当前商品是**锚点**，商品工具返回的是**候选集合**。

如果不区分，模型很容易把候选集合里的第一个商品当成「当前商品」。  
所以规则要明确：

```text
用户问当前商品本身时，只根据“当前商品资料”回答。
用户问搭配/推荐时，才使用商品工具结果。
```

### 4.5 为什么保留「不要编造、最多 4 件、输出 [[PRODUCTS]]」

这三条不是文风要求，是**输出契约和护栏**：

- **不要编造商品、价格、库存、折扣**：商品事实只能来自当前商品资料或工具结果，不能来自模型记忆。
- **最多 4 件**：前端卡片布局和回答可读性；避免模型堆一屏商品。
- **`[[PRODUCTS:id1,id2]]`**：给前端解析的标记，不是给用户看的。前端拿 ID 去数据库查卡片，不信任模型写的标题和价格。

补充约束：

```text
ID 只能来自当前商品资料或商品工具结果；没有有效 ID 就不要输出标记。
```

### 4.6 为什么「没有匹配结果」要加条件

原来的规则：

```text
如果没有匹配结果，直接说没有找到。
```

在「找新商品」时是对的，但在「问当前商品」时可能误伤：

- 用户问「这件是什么材质」。
- 商品工具没有搜到结果。
- 但 `product_context` 里明明有当前商品。
- 如果规则不区分，模型会说「没有找到」，而不是回答材质。

所以改成：

```text
如果用户要找新商品且没有匹配结果，直接说没有找到。
```

### 4.7 为什么「上下文为空不要装懂」

全局 `/assistant` 页面没有商品上下文。用户说「这件可以退吗」，模型如果假装知道，就会幻觉。

所以要有：

```text
当前商品资料为空时，不要假装知道用户在看哪件商品。
```

对应行为：

> 请告诉我是哪一件，退换规则按具体商品不同。

这对应评测集里的澄清类用例（如 A01、A21），不是随便加的话术。

### 4.8 为什么用变量选择器，不手打变量路径

Dify 的变量引用是内部路径。手打 `{{#start.product_context#}}` 容易出现：

- 变量名拼错
- Start 节点重命名后路径没更新
- 变量类型不匹配
- 选到了别的节点的同名变量

在 Prompt 输入框输入 `{`，从变量选择器里选 Start → `product_context`，能保证引用正确。

### 4.9 为什么规则要短、可测试

每条规则都应该对应一个评测失败类型：

| 规则 | 对应失败类型 |
| --- | --- |
| 当前商品本身用资料回答 | 拿错商品、商品事实错误 |
| 搭配/推荐才用工具 | 工具选错、推荐不相关 |
| 上下文为空先追问 | 该澄清没澄清、幻觉 |
| 不编造价格/库存 | 幻觉、违规承诺 |
| 最多 4 件 | 输出过长、推荐不相关 |
| ID 只能来自资料/工具 | 商品 ID 编造 |
| 没匹配说没找到 | 空结果硬编 |
| 不输出 `<think>` | 格式失败、内部推理泄露 |

Prompt 不是作文，而是**可回归的行为约束**。每次改一条规则，都应该能对应到评测集里的某类 case。

## 5. 推荐的完整 Prompt

```text
你是 Wardrobe 的导购助手。请根据“当前商品资料”和下面的商品工具结果回答。

当前商品资料（用户问“这件/这款/它”时优先使用；为空则忽略）：
{{#start.product_context#}}

规则：
- 用户问当前商品本身（材质、价格、颜色、尺码数据、退换政策）时，只根据“当前商品资料”回答。
- 用户问搭配/推荐时，才使用商品工具结果；不要把工具结果里的其他商品说成当前商品。
- 当前商品资料为空时，不要假装知道用户在看哪件商品。
- 不要编造商品、价格、库存或折扣，最多推荐 4 件商品。
- 如果用户要找新商品且没有匹配结果，直接说没有找到。
- 回答末尾必须输出 [[PRODUCTS:商品ID1,商品ID2]]，ID 只能来自当前商品资料或商品工具结果。
- 不输出 <think> 或内部推理过程。

用户问题：
{{#sys.query#}}

商品工具结果：
{{#body#}}
```

如果节点分成 System Prompt 和 User Prompt 两栏：

- System Prompt：角色、规则、信息源优先级。
- User Prompt：当前商品资料、用户问题、商品工具结果。

如果只有一个 Prompt 框，就按上面的顺序放在一起。

## 6. 不要这样做

### 6.1 不要把商品资料拼进用户问题

会污染意图分类和参数提取，推荐/相似款尤其容易坏。

### 6.2 不要保留「只根据商品工具结果回答」

商品工具没有材质、描述、护理和尺码数据；问这些时只能答错或编造。

### 6.3 不要用「文本」类型接 `product_context`

Dify 文本输入上限 256 字符，商品 JSON 会超。用「段落」。

### 6.4 不要让模型自己编商品 ID

`[[PRODUCTS:...]]` 里的 ID 必须来自 `product_context` 或商品工具结果；前端会按 ID 查库，无效 ID 会被丢弃。

### 6.5 不要把无结果规则写成「一律说没找到」

问当前商品时，工具没结果不等于当前商品不存在。

## 8. 常见故障排查

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| 回答仍是别的商品 | Dify Start 没有声明 `product_context` | 查 `/v1/parameters` 的 `user_input_form` |
| 回答仍是别的商品 | Prompt 还写着「只根据商品工具结果」 | 改开头的信息源范围 |
| 问材质答「没有数据」 | `product_context` 没有传到，或变量没插入 | 检查 `/api/chat` inputs、Dify Start 变量 |
| 问相似款只返回当前商品 | 把商品名拼进了 query，污染了检索参数 | 移除 query 拼接，改用 Start 变量 |
| 问当前商品答「没找到」 | 「无结果」规则没有区分场景 | 改成「找新商品且没有结果」 |
| 请求 400 或内容被截断 | Start 用了「文本」类型，256 字符上限 | 改成「段落」，最大长度 4000 |
| 回答带 `<think>` | 模型推理标签没分离 | Dify 开启推理标签分离；代理层也会剥离 |
| 商品工具 401 | `x-assistant-token` 不对 | 用 `.env.local` 的 `ASSISTANT_TOOL_TOKEN`，不是 Dify Key |

## 9. 可复盘的 AI PM 经验

1. **上下文工程不等于把资料塞进 Prompt**  
   动态上下文应该走结构化输入通道，用户问题保持干净，检索链路才不会被污染。

2. **工具 Schema 要按任务设计**  
   商品搜索工具只返回搜索和卡片需要的字段；商品详情用单独的上下文快照，不要求一个工具承担所有回答。

3. **Prompt 的核心是规定信息优先级**  
   「当前商品资料」和「工具结果」冲突时谁说了算，必须在 Prompt 里明确，否则模型会随机选一个。

4. **每条规则都要能对应评测失败类型**  
   拿错商品、空结果硬编、该澄清没澄清、商品 ID 编造、格式失败，都可以从规则层面预防。

5. **一次只改一个变量**  
   先确认上下文有没有传到，再改信息源规则，再调推荐策略；否则无法判断是通道问题还是 Prompt 问题。
