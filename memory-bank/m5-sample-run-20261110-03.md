## 后续补证：定位到提取的预算包含关系

用户补充的首轮 HTTP 片段不完整，以下仅整理明确出现的值，不把截断片段当作完整 JSON：

- requirements.q=摇滚风裤子、intent=outfit、category=bottoms、styleTags=[摇滚风]。
- status=needs_clarification、products=[]。
- clarification=[总预算是否包含搭配主体]。
- nextAction=先澄清一个缺失条件，不宣称无商品。

随后按要求，用户从第一轮「参数提取」的 text 提供以下四项（解码后的字段节选）：

```json
{
  "budgetCents": 50000,
  "budgetScope": "total",
  "includeCurrentProduct": null,
  "missingInformation": []
}
```

已确认的错误位置是提取节点的 includeCurrentProduct：原任务是买指定上衣再配裤子，两件总预算500元，应为 true，实际却为 null。金额及 total 正确，品类也正确。

源码 `src/lib/assistant-samples.ts` 明确在 outfit + total + includeCurrentProduct=null 时加入“总预算是否包含搭配主体”。澄清列表不为空会使 status=needs_clarification、products=[]。本轮原始提取值、HTTP 澄清、最终追问在这一点上相互吻合；无需再把首轮解释成回答节点忽略了 over_budget。尚未取得代码执行节点完整输出，不声称已逐节点核验全部字段，但不影响已观察到的提取错误。

首轮 missingInformation=[] 不代表包含关系已确定：工具会自行检查必要字段并补充澄清原因。null 不是 false，不能在 HTTP 或代码中无条件改成 true。

修复指导：替换提取 SYSTEM 中 includeCurrentProduct 的原定义，明确主体可由顾客点名；“买A再配B、两件总预算”已经表达包含主体，不能因缺商品ID/product_context就判未知；已拥有主体或仅给搭配单品预算时仍为 false，真正不清楚时保留 null。缺商品页面上下文是否造成模型此次误判只是可能解释，未被证明；本次修复基于明确语义规则，不宣称查明模型内部原因。
