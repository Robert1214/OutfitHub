# 真实商品首题：HTTP 400 参数校验阻断

日期：2026-11-11。状态：已定位到外层查询参数校验；实际违规参数尚待确认，Dify重测未完成。

## 原始证据

建议测试题是“找一条极简风裤子，单件预算400元，不要鞋”。用户报告第一题HTTP失败，最初口述404，随后明确纠正为400，并提供products接口地址及body：

```json
{"error":"完整需求查询只接受requirements、limit和contextProductId，请检查节点参数"}
```

以用户纠正后的400及实际body为准。没有取得同次完整查询参数，不能断言是某一行没删除、limit仍为5或用户未保存。粘贴链接末尾带中文句号，但上述body来自目标路由，不能只因粘贴标点就判URL错误。

## 判断与本地对照

该错误来自products路由的catalogQuerySchema或重复键校验，发生于requirements内部JSON解析及商品查询之前。它证明请求已到达目标处理逻辑，且本次鉴权/限流未阻断；不能视作没有商品，也不能据此认定LLM需求提取错误。

现有错误文案将键名、值范围和重复键错误合并，不能仅凭这句文案确定具体原因。本地复现：

| 对照 | HTTP与结果 |
| --- | --- |
| requirements合法、limit=4、contextProductId为空 | 200，matched_known_constraints，黑色高腰阔腿裤359元 |
| 只把limit改回旧值5 | 400，同用户错误 |
| 只增加旧q参数 | 400，同用户错误 |
| 只重复requirements参数 | 400，同用户错误 |

错误也可能来自空/超长requirements、无效limit、超长contextProductId等外层校验。本次尚未进入内部JSON或业务语义判断。

## 最小处理与待验

仅核对HTTP Params：只保留requirements=代码执行.requirements、limit=4、contextProductId=用户输入.product_id，大小写准确、各一行；删除q/category/styleTags/anchorSampleId等旧行。尤其原配置limit为5，新分支只接受1至4。

无需修改提示词、重启服务或换端口。修正后重测原400元题；若仍400，取得Params或实际GET查询参数，不要Header。本轮未操作Dify、未改业务代码、未发布。原始失败与本地对照分别记录，不将本地200视作Dify首题通过。
