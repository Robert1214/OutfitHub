### P2 结论（已补测，确认为工具缺口）
预算 400 元、口径「只买下装」时，工具仍返回整套方案并按 818 元合计描述。**原因**：`src/lib/assistant-outfits.ts:121` 虽在 checkedConstraints 记录了"仅新购买下装的预算"，但 `assessedPriceCents` 只区分是否计上衣（false → 359），没有任何字段告诉回答节点"本次只应在正文里报 359、不报 818"。回答节点因此照抄 outfitTotalCents。
影响：顾客说"预算 400 只配裤子"，可能被告知"818 元"。当前 400 ≥ 359，未触发超预算拦截，属于漏网；若限制为 300 元则会被判超预算 59 元。
修复方向（需用户同意后改代码）：下装单件口径时，在返回体增加 `reportedPriceCents` 或让 products/outfits 只携带下装金额；并同步回答规则。**未改代码**。

### D1（新，阻断性）· 同会话第 2 轮起 Dify 返回 400
- 现象：带 `conversationId` 的续轮，`/api/chat` 返回「导购助手暂时不可用」；`assistant_logs.error = dify_404`（实际映射的是 `dify_${status}`，本次 Dify 状态为 400）。
- 定位：直接 curl 本地 Dify `/v1/chat-messages`（带真实 Key）：
  - 首轮 `你好` → 200 ✅
  - 任何后续请求（含全新 user、全新 conversation_id、`你好` 这种最简单问题）→ **HTTP 400 `bad_request`**，约 6 次连续全部失败。
  - 说明不是我们的 body、不是额度、也不是"续轮逻辑"问题，而是 **Dify 服务端当前态**（执行约 1~2 次即进入异常，至堆栈/变量/插件/内存之一）。
- 影响：多轮对话、T1 复测、全量回归都无法进行，当前网站导购在第二次对话起即不可用。
- 待办：调大 Dify API 容器日志（`LOG_LEVEL=DEBUG`，看 flask/werkzeug 是否记录 400 原因）或重启 API 容器；如可复现需在 Dify 侧定位。**未改任何配置**。
