## PM-001：为什么选对商品仍不能直接判通过

日期：2026-11-10。环境：已有 Dify Chatflow 草稿，开发端口 3000，三件内部样例 rock-outfit-v1。

### 1. 顾客要完成什么

本轮给用户的测试题为：

> 我想买滚石巡演图案 T 恤，再搭配一条摇滚风裤子，两件总预算 800 元。请推荐合适的搭配并说明理由。

用户未重新粘贴实际 query；已取得的证据是两次 HTTP body 和最终回复。不能把建议输入当成逐字核验过的实际请求。

指定的 T 恤是搭配主体，尚需寻找的候选是裤子。一起购买意味着总预算包含两件，不意味着尚需搜索两个候选品类。成功推荐必须同时保留品类、风格和总预算，解释搭配依据。

本轮 HTTP 参数固定 anchorSampleId=S01。它让工具返回指定 T 恤资料，没有验证 AI 能否从商品名称识别真实商品 ID，也没有验证商品页面中的“这件”能否正确指代。

### 2. 先读懂 body 中与决策相关的字段

body 是商品工具返回给回答节点的资料与结果；它本身不是最终顾客回复。下面的含义来自本项目的接口约定，不是所有 API 的通用定义。

| 字段 | 普通话解释 | 验收时怎么用 |
| --- | --- | --- |
| requirements | 工具收到并回传的需求 | 对照顾客原话，检查遗漏、曲解、旧条件残留；不是商品事实 |
| currentProduct | 本轮指定搭配主体的资料 | 核对是哪件商品、价格和已知资料；本例来自固定 S01 |
| status | 工具对本次请求的判断 | 决定当前能否推荐、是否要澄清或协商预算 |
| products | 本次通过工具已检查条件的候选 | 新增推荐从这里选；仍需核对工具未覆盖的顾客要求 |
| evaluations | 候选的检查记录及原因 | 可解释不适配或超预算；不能当作备用推荐列表 |
| clarification / nextAction | 缺什么、下一步如何处理 | 回答是否按结果行动；已明确的条件不应要求顾客重复说明 |
| assessedPriceCents / differenceCents | 计入预算的金额、预算减该金额 | 单位是分：55600=556元；差额负值表示超预算 |

### 3. 怎么从第一次结果发现问题

| 对照项 | 顾客意图或工具约定 | 实际证据 | 判断 |
| --- | --- | --- | --- |
| 候选品类 | 明确找裤子，应为 bottoms | requirements.category="" | 传给工具的需求丢失了已知品类 |
| 检索关键词 | 应描述待找的裤子 | q 包含上衣名称和裤子 | 主体与候选混在一起，需澄清定义 |
| 工具判断 | 缺少品类则暂不输出成功推荐 | needs_clarification、products=[] | 工具按既有约定要求澄清 |
| 最终回复 | 成功推荐必须与工具状态一致 | 回复直接选择刷蜡涂层紧身裤 | 本次推荐只能在 evaluations 找到，绕过了工具状态 |
| 商品和金额 | S01+S03，188+368=556，余244 | 回复确实选对并算对 | 这些单项满足，不能抵消前面的链路问题 |

evaluations 中 S03 的 candidateMatches=true，只表示它通过了记录中的风格/适配检查。它不代表整次请求已经完成校验：本例仍缺 category，工具明确没有将它放入 products。

因此，首次记录为“选款、金额正确；提取与工具结果处理不一致，集成未通过”。不能因为最终答案看起来合理，就忽略中间证据。若同样越过工具状态的行为出现在超预算场景，可能把预算不满足的商品当作成功推荐；这是待检验的风险，不是本轮已经发生的另一条失败。

### 4. 已确认的原因与尚未证实的解释

已确认：工具收到 category 为空；接口代码据此返回 needs_clarification 和空 products。最终回复与该结果不一致。

直接 HTTP 对照保持其余输入不变，仅将 category 从空字符串改为 bottoms，接口即返回 matched_known_constraints、products 包含 S03、clarification 为空。这验证了空品类字段对本次工具结果的影响，没有验证模型为何漏提取。

可能的上游解释：旧提取提示词写了“需要多个品类时填空”，可能让模型把“两件一起买”理解成“两个候选品类”。但没有取得本次提取节点完整输入、输出及 UI 配置快照，不能断言这就是唯一根因，也不能完全排除传递环节的问题。

本次指导的不足也需要保留：临时回答说明没有充分写明“先检查 status、不得从 evaluations 兜底推荐”；测试提问最初用了“这件”，而预览没有传入当前商品 ID，后来已改用明确名称。

### 5. 采取了什么处理，为什么

1. 修订提取提示词中 q/category 的定义：区分“已指定主体”和“尚需寻找的候选”。一起买影响计价，不把已指定上衣再算成一个待搜索品类；没有硬编码所有请求都为 bottoms。
2. 补充回答规则：先检查 status；成功推荐只从 products 选择。evaluations 保留作原因和金额解释，尤其供超预算时说明差额；不能直接升级为满足条件的推荐。
3. 按原语义新开会话重测 800 元题，核对提取、工具与回答三处是否一致。没有通过改商品价格、强行更换顾客要求来让测试通过。
4. 原始失败单独保存，重测另建记录。Dify UI 由用户操作；本地文档是指导与证据记录，不等同于实际 DSL 配置备份。

配置说明见 [Chatflow 提取规则](m5-dify-chatflow.md) §12.1 和 [样例工具操作](m5-sample-tool-setup.md)。本轮处理没有改变正式商品库或样例接口业务代码。

### 6. 重测证明了什么

| 关键项 | 第一次 | 重测 |
| --- | --- | --- |
| q | 上衣名称 + 摇滚风裤子 | 摇滚风裤子 |
| category | 空 | bottoms |
| status | needs_clarification | matched_known_constraints |
| products | 空 | 仅 S03 |
| 最终选择 | S01+S03，但与工具决策不一致 | S01+S03，与工具结果一致 |
| 金额 | 556元，余244元 | 556元，余244元 |

结论：本次 800 元具体用例的核心流程通过。成功状态的这一次重测，不证明 needs_clarification 分支以后一定被正确处理；500 元超预算分支和 500→600 同会话条件保持仍待验证，也不证明真实检索、库存、合身或下单率提升。

顾客文案另列待改：重测仍写“S01–S03 这组样例”，把内部编号暴露给顾客；“只靠基础款硬凑”是无必要的比较。裤子的具体尺寸、材质、库存和退换尚未确认，不能编造；但无需把内部核验过程全部朗读给顾客。已有尺寸与合身结论也要区分：S01 有部分尺寸数据，不等于已验证合身。

### 7. 这是产品经理需要掌握的什么能力

本项目的 AI PM 需要能定义正确行为，并用证据判断系统是否达到；不要求先学会实现每个字段或定位每行代码。

| 产品经理应能做的判断 | 工程或 AI 辅助核验 |
| --- | --- |
| 从顾客话里提取明确条件，区分商品主体、候选和预算范围 | 追踪各节点输入输出及映射 |
| 发现工具判断与最终回复矛盾，要求查证 | 检查字段校验、过滤逻辑、执行日志 |
| 区分正确答案、可靠处理流程和顾客体验 | 构造受控对照、定位修改点 |
| 决定哪项满足、哪项待修，并说明证据边界 | 保存原始记录，汇总重测结果 |

学会的判断可以用四个问题练习：顾客说过的条件有没有丢？推荐和金额有没有资料依据？工具状态与回复行动是否一致？顾客读完是否知道下一步、有没有被内部术语干扰？

这次分析与整理由 AI 辅助完成，用户提供商品审美正反例、操作 Dify 并回传实际结果。复盘时用户可用自己的话解释上述判断；不能把阅读本复盘自动记为本人独立完成了故障定位。

### 8. 遇到空 products 时，下一次怎么判断

先看请求是否成功，再看 body 的状态与原因，不直接断言店里无货。

| 证据 | 正确判断方向 |
| --- | --- |
| 请求报错、超时、401或402等 | 工具或模型调用未正常完成，不能推导商品供给情况 |
| needs_clarification + 空 products | 先对照顾客原话：真缺信息才问顾客；已经说过则查提取与传递 |
| over_budget + 空 products | 检查是否存在风格适配但超预算的组合，说明金额，征求顾客是否调整 |
| no_known_match_in_samples | 仅说明本组已知资料内没有确认匹配，不能外推全店或市场 |
| matched_known_constraints + 有候选 | 核对推荐确实来自候选、金额正确、剩余未知条件没有被编造 |

本接口的 status 是约定的一部分；其他接口字段不同，需要先查清含义。空列表可能来自资料缺失、提取/映射错误、检索漏召回、约束排除或实际供给不足，几种情况的处理方式不同。

## PM-002：允许多轮，不等于重复确认已知条件

日期：2026-11-10。用户测试500元总预算问题，截图中助手先确认预算是否包含T恤，用户回答“对的”，助手随后说明556元/超出56元并询问是否调整到556元。

用户问“两个问题是不是不符合预期”。判断要拆开：截图是两轮各一个问题，未违反“一次只问一个问题”；但第一问重复确认已明确的预算范围，增加了不必要的交互，首轮未达预期。第二问是在真实预算冲突后征求调整意见，合理。具体原文和判定见[运行记录](m5-sample-run-20261110-03.md)。

### 为什么必须确认日志属于哪轮

用户最初同时提供 `status=over_budget`、`products=[]`。不能据此直接说首轮“明知超预算仍问预算范围”：追问后用户明确，这两个字段来自回答“对的”之后的第二轮。

因此，当前证据支持“首轮行为冗余、第二轮工具和回答对上”，还不支持“首轮提取正确”或“首轮回答忽略工具状态”。诊断时必须将同一轮的顾客输入、提取结果、HTTP body 和回复配对；不同轮的数据不能拼成一次成功或失败的证据。

### 下一步如何定位

先取首轮 requirements、status、clarification、nextAction。若首轮已是 over_budget，核对回答节点确实收到本轮 body 后检查回答规则；若首轮是 needs_clarification，或 total/includeCurrentProduct 等已知条件丢失，先检查提取和传递。不凭第二轮状态直接修改首轮提示词。

产品规则的重点是“问能推进需求的必要问题”。条件确实不明时澄清；条件已明确时直接使用；条件冲突时才问是否调整。确认预算范围和同意提高预算是不同授权：用户“对的”只承认原500元含两件，没有同意加价。

上述为第一阶段取证过程；当时仅有第二轮 HTTP，不能直接归因。随后用户补齐了第一轮证据，定位如下。

### 补齐第一轮证据后怎样更新判断

首轮 HTTP 为 needs_clarification，澄清原因是“总预算是否包含搭配主体”。用户随后从首轮提取节点提供50000/total/includeCurrentProduct=null/missingInformation=[]。

这说明金额和预算范围被识别，但“预算是否包含已指定上衣”被提取成未知。工具代码遇到 outfit + total + null，会主动加入该澄清原因，因此回答节点顺着工具追问。应先修复提取定义，不能仅要求回答节点忽略澄清，也不能把问题继续归为首轮回答忽略 over_budget。

PM 的判断点：同样是“用户被多问一次”，错误可能在回答，也可能更早出在需求提取；找到同轮最早出现的错误值，才能选对修改位置。missingInformation=[] 也不能单独说明资料齐全，工具会检查其他字段。

修订规则明确“买指定A、再配B、两件总预算”表示包含A，includeCurrentProduct=true；主体可由用户点名，不依赖商品ID。已拥有或预算不含主体时为 false，确实未知时为 null。没有把所有总预算固定为 true。该阶段只有规则草稿，不能当作已修复；随后实际重测见下。

### 500元重测结果

用户随后确认提取与HTTP关键字段符合预期，并给出实际回复：直接说明188+368=556、超预算56元，再问是否愿意调整到556元，没有重复确认是否包含上衣。该用例超预算处理通过；本次完整日志未重贴，字段部分依据用户确认，见[重测记录](m5-sample-run-20261110-04.md)。

“店主也确认”这类内部口吻仍待优化。顾客尚未接受提高预算，任务处于协商；600元续轮尚未验证。这体现了三个不同结论：回复按预期处理了冲突、顾客是否接受方案、整组多轮是否通过，需要分别记录。

### 字段教学：如何把一句需求变成判断

用户要求解释字段含义与判读方法。下面是本项目样例接口的约定与本题预期，不是本次完整HTTP原文。

| 提取字段 | 本题应表达什么 | 为什么检查它 |
| --- | --- | --- |
| q | 摇滚风裤子 | 查找候选，不混入已指定上衣 |
| intent | outfit，找搭配 | 明确任务是组合搭配，不是独立搜单品 |
| category | bottoms，下装 | 品类是待找的裤子，不是订单里所有商品 |
| styleTags | 摇滚风 | 记录顾客风格要求，不把所有商品标签都加成约束 |
| budgetCents | 50000，即500元 | 金额用整数分，避免误读成50000元或把500元写成500分 |
| budgetScope | total，合计预算 | 要核算组合，不是仅判断裤子368元小于500元 |
| includeCurrentProduct | true，计入上衣 | 指明合计金额包含指定T恤 |
| otherRequirements | 其余明确要求，如指定上衣 | 检查未丢掉主体、排除项等条件 |
| missingInformation | 本任务理解上仍需明确的信息 | 空列表不是库存/尺寸/退换资料都齐，也不能代替工具对其他字段的校验 |

budgetScope 和 includeCurrentProduct 要合看：前者说明预算按单件还是合计，后者说明合计里是否包含搭配主体。只有总预算total，未必已经知道主体要不要算钱。以这组两件样例为例，total+true计入188+368；明确已有上衣、预算只买裤子则不计188元；null表示未知，不能当false或0。具体语义以用户原话为准。

| 工具返回字段 | 含义与本题判断 |
| --- | --- |
| status=over_budget | 已记录风格/适配规则下有组合，但预算不足；不是缺预算信息，也不是工具调用报错 |
| products=[] | 没有通过本次已检查条件的推荐候选；结合状态看是预算排除，不代表全店无货 |

| clarification | 工具检查后需澄清的条件；会补充提取的missingInformation未列出的缺口 |
| nextAction | 工具建议下一步；超预算时说明限制并询问是否调整，不能擅自改预算 |

| differenceCents | 预算减计入金额；50000-55600=-5600，负值表示超56元 |
