## 7. 第二轮用户判断与判分草案

### 用户原话

> 1、这些困难有我自己遇到的、也有朋友跟我说的，真实的情况是问店员寻求解决，他们会根据自己的经验来帮你挑选、搭配，不满意再换、再改进，比较依靠人的自身判断；2、需求理解准确无偏差，推荐的商品满足几个条件其中之一或多个：1是由需求中提取的关键词如”上班“、”通勤“进行知识库检索匹配得到的商品。2是根据我制定的审美标准推荐的商品比如通勤上班我会要求推荐较基础的款式，衬衫西裤之类的，且不会出现蓝色加绿色这种不协调的搭配。3是推荐搭配时会配上风格介绍，比如一身黑就是素、低调，蓝+棕就是高级有气质等等；3、如果推荐出现了鞋子、浮夸花哨的款式、不符合我的审美标准的情况，都是失败。

### AI 整理与需要区分的事项

- 需求来源已补充，仍不能据此推断发生频率、需求规模或商业提升。
- 现有替代方案是店员提供建议并根据反馈调整。可继续验证助手能否理解“不喜欢”的具体原因并调整；此项为后续评测候选，未新增正式验收要求。
- 关键词检索、审美规则属于推荐依据；不能用任意一个依据命中，抵消顾客明确的预算或品类要求。
- 当前项目的商品事实通过数据库商品工具查询，支持风格/场合标签；政策/FAQ 等通用内容走知识库。用户提到“知识库检索”先按概念澄清处理，不视为授权变更商品数据架构。商品级退换仍依据具体商品字段。
- 审美标准按用户提出的店铺风格偏好记录。“蓝绿不协调”“蓝棕高级”等不能自动上升为普遍事实；颜色深浅、饱和度、面积比例及例外尚未定义。
- 衬衫、西裤是用户举出的基础款例子，尚未定义为唯一可推荐类别；也不能忽略练习中顾客“别太正式”的要求。

### 本题判分草案（待核对，不改正式评测）

| 维度 | 候选检查方式 | 来源与状态 |
| --- | --- | --- |
| 需求理解 | 保留总预算 800 元、上衣一件、裤子一条、通勤、不过于正式，不擅自改写条件 | 练习原话；AI 转成可核对项 |
| 预算与品类 | 作为完整搭配交付时，总价不超过 800 元，构成为上衣加裤子；推荐鞋子则不符合本题 | 预算来自练习，鞋子为用户明确失败例 |
| 商品事实 | 推荐来自实际商品数据；价格、库存、材质、退换描述有依据 | 现有项目约束；本轮未实测 |
| 审美与场合 | 基础、不过于花哨，符合用户制定的适用规则；规则不足时不能让评分者自行猜测 | 用户提出；具体规则及适用范围待定 |
| 推荐解释 | 说明所选商品组合的风格，以及与顾客场合和偏好的联系；文案需与实际商品一致 | 用户要求风格介绍，AI 补充可核对方式 |

区别：合适的完整搭配、库存不足时的合理应对、违反约束的推荐，应分别记录。无匹配时不能因为没有成交就自动认定助手违规，也不能把只推荐一件当作已完成整套任务；具体判分由用户确认。

### 已讨论的选项：没有完全匹配的商品时

练习条件仍为总预算 800 元、上衣加裤子、基础通勤且不过于正式。假设当前库存无法同时满足全部条件。

- A：说明缺少完整匹配，再只问一个问题，由顾客决定是否调整某项条件。优点是尊重原约束，代价是多一轮沟通。
- B：说明无法凑齐，先展示符合条件的单件，明确仍缺哪件。优点是先给可用结果，代价是当前任务尚未完成。
- 可由用户提出组合策略或其他做法；不默认放宽预算，不擅自将鞋子替代裤子。

## 8. 决策 D01：无完整匹配时先协商条件

> 用户原话：选择A，我的原则是ai多几轮沟通也无所谓，但是能解决顾客需求即可

- **选择：** 在当前商品中找不到满足全部已知条件的完整搭配时，先说明没有完整匹配，再一次询问一个问题，由顾客决定是否调整条件。
- **理由：** 用户愿意接受必要的多轮沟通，以解决顾客需求为目标；单轮立即出推荐不作为优先目标。
- **代价：** 可能增加等待时间和沟通轮次，效果仍需验证；不能把愿意多聊视为已经解决问题。
- **约束：** 顾客确认前，不自动增加预算、改变品类或放宽风格要求；确认后按更新的条件继续查找，保留未被修改的条件。
- **实现状态：** 已同步 PRD §7.10 与 M5 契约；尚未修改代码、Dify 配置或正式评测 CSV，也未运行验证。
- **尚未决定：** 顾客拒绝调整、没有可行候选或多轮仍无法满足时，如何结束或提供演示转人工；未约定固定轮次上限。

后续验收候选（待用户确认）：区分“正在澄清”“已给出满足更新条件的搭配”“仍无法满足”；记录条件是否保留、问题是否推进，以及最终是否解决，不把多轮本身视为成功或失败。

### D01-1 收尾：顾客不愿调整条件（2026-11-14 用户拍板）

假设顾客回复“800 元不能加，上衣和裤子也都要，风格不想改”，且现有商品确实无法满足。

- 已否决 A（只说无法满足后直接结束）：顾客拿不到任何可用信息。
- 已否决 B（询问是否转人工）：你 2026-11-09 指出商品确实不存在时转人工也解决不了，失败分类表也写了「人工不自动解决缺货」。
- **选择 C：说明无法匹配 + 展示部分符合条件的单件（标明不符合哪条、不当作推荐）+ 给出两个出口（调整条件 / 结束），最后弹出演示转人工提示。**
  - 「部分符合」指品类/风格/场景等非硬约束匹配、但明显违反硬约束（预算、明确排除项）的商品；只列差在哪里，不把它说成「推荐」或「可以接受」。
  - 价格差要算准（如超出 ¥56），不得编造优惠或降价。
  - 转人工为演示提示（不真实联系客服），在收尾之后出现，不作为解决商品缺口的承诺。
  - 依据：用户原话「这时候弹出转人工提示」；沿用 C 的「无解时仍给出可用信息」。
  - 代价：结束时多展示 1~2 件，可能引起顾客误以为被推荐；因此必须显式标注「不符合哪条」。

### D01-2 判分标准（2026-11-14 用户拍板，冻结）

采用**宽松标准**，一条对话的结局分三类：

| 结局 | 判为 | 说明 |
| --- | --- | --- |
| 给出符合已知约束（预算、风格、品类、排除项）的完整搭配 | **完成 ✓** | 金额、口径、marker 准确；不编造 |
| 确无匹配，按 D01-1 正确收尾（说明 + 部分信息 + 出口 + 转人工提示） | **完成 ✓** | 没有买到东西也算完成；收尾错误（编造、只说「没有」、擅自改条件）判失败 |
| 正在追问/澄清，或等待顾客答复 | **协商中 ◐** | 不计入通过，也不计入失败；同一会话后续轮有结局后按结局判 |
| 答错、编造事实、丢失顾客条件、违反「确认前不擅自改条件」 | **失败 ✗** | |

- 计分单位是**会话**（一个 caseId 的全部轮），不是轮次；会话内任意一轮达到「完成」即整个会话完成。
- 分母 = 参与评测的会话数；「协商中」不计入分子也不计入分母（单独报告数量）。
- 禁止用「技术通过 17/17」替代本判分；技术通过只是前置条件。
- 冻结版：本判分自此作为 `ai-pm-user-task-card.md` 的验收依据；如需修改须写下理由与新版本日期。


## 9. 用户对无结果原因的追问（2026-11-09）

> 用户原话：我想明确一个问题：店里没有符合条件的组合这件事，可能是因为我的知识库、匹配策略不完善吗，还是实在找不到？如果是第二种转人工也无济于事

这是本次实际发生的证据审查：用户要求先区分系统能力缺口与商品供给缺口，指出 AI 先前提出的转人工建议未说明人工能解决什么。这里只记录用户已提出的质疑，不替用户决定新规则。

### 当前证据

静态阅读 `src/app/api/assistant/products/route.ts`：普通搜索依赖关键词/同义词、商品字段与标签评分，并截取返回候选；当前商品的搭配分支按互补品类、风格/场合标签及同色加分排序候选单品。该工具未提供完整组合穷举与排除原因的证明。因此单次返回空或未返回所需组合，不能证明整个商品目录没有可行组合。本轮未启动服务、未查当前数据库，具体请求的根因仍未知。

商品事实仍走数据库工具；应分别检查商品字段完整性、用户条件提取、检索覆盖、组合生成与回答组织。完善通用知识库不必然解决这些问题。

### 待讨论的诊断方法（建议，未实施）

| 情况 | 判断所需证据 | 相应方向 |
| --- | --- | --- |
| 商品存在但资料缺失 | 商品资料/实物依据与数据库字段核对 | 补真实资料；未判断的风格不能当作不符合 |
| 商品资料充分但检索漏掉 | 已知符合条件的商品与查询参数、过滤、候选结果对照 | 修正条件提取或检索，不要求顾客为系统漏检放宽需求 |
| 候选有可行组合但未组出 | 候选组合、总价和已确认审美规则逐项核对 | 修正搭配生成与约束检查 |
| 核对后确无符合组合 | 当前在售数据完整，在约定规则范围内检查相关组合并说明淘汰原因 | 说明具体供给限制；是否调整条件按 D01 由顾客决定，人工不自动解决缺货 |
| 资料、规则或工具状态不足以判断 | 缺失字段、规则歧义、工具错误或未覆盖候选 | 如实保留不确定性；人工只有能补充资料或判断时才有实际价值 |

对于本项目现有小规模商品样例，可先人工核对相关上衣与裤子组合，建立已知答案，再检查系统是否找出；数量、真实库存和审美判断以实际核对为准。是否执行、具体用例和验收标准后续由用户确认。

D01 的“无完整匹配”触发条件需要进一步明确，不能自动等同于第一次检索无结果。当前先讨论这一前提，暂不继续要求用户选择收尾话术。
