## 已确认的原因与证据边界

需求提取正确：没有指定品类、风格或搭配主体，预算500元。工具状态要求澄清也正确。但原样例代码总是先用固定anchorSampleId查出currentProduct，只有多品类选择分支手动清空；未知品类和独立搜索仍返回S01，同时附带无关候选evaluations。

用用户提供的相同requirements和既有S01参数执行原代码，新增测试确实得到S01作为currentProduct。两个新回归检查和扩展HTTP路由检查失败，其他12项通过。这证明本地接口的来源混淆确定存在，能解释模型为何看到该商品；未取得用户首轮currentProduct，不伪称读到了那轮完整HTTP或证明了唯一模型内部原因。

回答层又把商品资料误归因于真实页面，并在被追问后坚持该说法。这不是普通冗余文案，是来源不实。商品名称/价格可以来自查询结果，但不能由此证明顾客正在浏览、已经选择或页面已提供该商品。助手自己此前的话也不能作为新的外部证据。

## 已完成修复

- 未知品类：先澄清，currentProduct及currentProductSource为null，products/evaluations为空；固定样例不再流入该回复的数据来源。
- 独立搜索：不带入固定主体，也不因anchorSampleId配置而排除该商品。搜索摇滚上衣时S01可以是查询结果，但不是当前浏览商品。
- 已明确候选品类的outfit计算保留原样例价格/适配逻辑；兼容currentProduct字段，标明currentProductSource=internal_sample_anchor，明确不提供页面浏览证据。outfit提取仍不能独立证明顾客已选哪件，必须结合真实对话；本修复不宣称已实现通用商品身份解析。
- 提示词准备：在原【内部样例工具判断】中替换已有的currentProduct那一段，明确真实product_context、工具样例与对话选择的区别，不能用旧回答补造来源。见m5-dify-chatflow.md §12.14。Dify未由AI修改。
